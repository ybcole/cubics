## M05 profile lifecycle implementation — 2026-11-14

[Commit d8a9f378](https://github.com/ybcole/cubics/commit/d8a9f37827b660322956e84572c204d484367385) introduces a **separate non-persistent Shared profile** per verified Clerk account/widget on the current Electron device: `cubics-shared-<account>-<widget>` (no `persist:` prefix). It cannot silently inherit credentials from either the existing account-scoped persistent Personal profile (`persist:cubics-personal-...`) or a widget-scoped persistent Live profile (`persist:cubics-tab-...`). Only the main process creates and authorizes these partitions. User starts Shared hosting explicitly; the mode remains visible. Existing Personal and Live partitions are left unchanged to avoid unexpectedly losing saved sessions.

The Personal tab UI now offers **Clear local Personal browsing data**; Shared tabs provide a scoped clear control while not hosting. A native confirmation is required. Electron re-checks the authenticated identity after the dialog, derives its own partition name, requires a previously issued local session capability, destroys its active guests, and uses Electron 45 `Session.clearData()` for the selected partition. It notifies attached UI tabs to remount; it does **not** erase Clerk's default-session cookies, the database, another user's partitions, OS credential stores, saved downloads on disk, or historical cloud widget URLs. A cancelled dialog changes nothing.

[Cross-platform fixture commit 13f5042](https://github.com/ybcole/cubics/commit/13f50421095a454c5a1408362d62214e3f7228a6) additionally tests actual Chromium cookie jars across modes and account switches and verifies that clearing the Shared jar leaves Personal and Live cookies untouched. The fixture is simulated login, not real Clerk. **M05.01/M05.02/M05.03/M05.06 remain open for full milestone certification** (formal local BrowserProfile IDs/controls, actual Clerk two-account integration, OS-restart persistence, data export/deletion policy, and shared controller/consent E2E are not complete). Native matrix for the cookie assertion commit must finish successfully before it is called passing.

Security controls: [Electron main](../../electron/main.js), [profile policy](../../electron/security-policy.cjs), [native tests](../../scripts/security/electron-native-e2e.cjs), and [IPC inventory](../security/runtime-inventory.json). No provider or database migration was performed.

## Non-owner Live/Shared metadata hardening (2026-11-14)

In addition to Personal redaction, the legacy and versioned workspace widget reads now share the same `redactWidgetForViewer` function. Non-owner Live titles become `Live tab` and their URL is suppressed; non-owner Shared tabs show `Shared tab` and at most the origin (protocol/host/port) of the chosen site. Full paths, query strings, fragments and user-supplied titles remain visible to their owning account only. The v1 `safeUrl` summary never includes paths, even to the owner. Owner-controlled interactive Shared tab navigation still uses the full authenticated record in the host's view; a new host may need to navigate to the specific page after taking over. Per-mode safe site disclosure policy and negative tests are implemented, but existing cloud records still persist original URLs and actual two-account acceptance remains pending.

**Snapshot consistency:** The legacy v1 snapshot now uses the same server-side viewer redaction as both widget-list endpoints, preventing an unowned or non-owner Live/Shared title from bypassing the generic title policy. Read compatibility remains unversioned; this does not prove real multiaccount deployment or eliminate historical private URL records.

## M05 device-local BrowserProfile identity and metadata export (2026-11-14)

A new [Electron profile helper](../../electron/browser-profile.cjs) atomically persists one random non-secret device marker per Electron `userData` directory and deterministically derives opaque `bp1_...` BrowserProfile IDs from the device marker, **verified** Clerk account ID, mode and (for Live/Shared) widget ID. Room membership is not part of the identity. The profile ID is not a login token, not a security grant and never replaces the main-process authenticated partition check. Personal and Live cookie partition names are preserved; Shared remains temporary. Device markers/IDs stay on the device; no Prisma schema or cloud/sync records were changed.

Native `getBrowserProfileInfo` and `exportBrowserProfileInfo` IPC demand the current authenticated user and a previously issued partition. The Personal tab offers a **metadata-only** export through an OS save dialog; Electron verifies the account again before writing to a new local file. The JSON describes the opaque profile ID, mode and persistence but contains **no cookies, browsing history, site URLs, credentials, or raw account ID**. This is **not** a full browser-data export. Complete migration, account sign-out, profile inventory/retention and full export/delete remain M05.06 dependencies. Tests assert stable per-device/profile derivation and deny malformed identities.

## Two-process native restart fixture (2026-11-14)

[OS runner](../../scripts/security/run-electron-native-e2e.cjs) now launches the security/cookie fixture, terminates Electron after its explicit PASS marker, then **launches another Electron process against the same isolated device profile**. [Restart assertions](../../scripts/security/electron-profile-restart-e2e.cjs) verify a saved opaque BrowserProfile ID and separate Personal/Live cookies persist across OS process shutdown while an in-memory Shared cookie does not. They also reject an attempt to claim a different account after restart. The first process flushes persistent cookie stores before shutdown. ## Immediate account-change revocation (2026-11-14)

A [root-level Clerk listener](../../src/components/DesktopBrowserAccountBoundary.tsx) now informs Electron of signout/account switches. The main-process `cubics:notify-browser-auth-change` IPC accepts only the trusted top-level app renderer, revokes the previous account only if it still matches the **actual** verified main-process account, destroys active guests and clears partition/capture grants. A stale notification from the old account cannot revoke a newer account. `onBrowserAccountRevoked` also removes stale renderer browser grants without exposing the untrusted raw Electron IPC channel. Existing partitions remain on disk until explicitly cleared. Native tests simulate stale/signed-out account notifications. This supplements server-authoritative `/v1/identity` checks; it does **not** certify Clerk's production login/logout integration nor guarantee revocation under a compromised renderer or disconnected authentication service.

## Retired Shared navigation URL relay (2026-11-14)

The legacy Socket.IO `sb:nav` handler allowed an authorized member to broadcast an arbitrary full Shared URL (including sensitive query/fragment data) across a room. This channel was not consumed by the current Shared/Live client. It has been removed, and a real-socket negative test asserts that attempted `sb:nav` packets are not emitted to another room member. Shared media/control stays on its explicit viewing transport; authenticated REST remains the source of permitted coarse metadata. This is a M05.04 hardening item, not proof that all legacy private URLs have been migrated off PostgreSQL.

### Native restart Linux process cleanup (2026-11-14)

The shared-display follow-up [run 43538684350](https://github.com/ybcole/cubics/actions/runs/43538684350) still failed the Linux **second-window startup** while macOS/Windows passed. The CI supervisor now observes the actual Electron fixture PID, enumerates descendants of the spawned Linux process, kills the full tree after the explicit PASS marker, and records if a second process quits before window creation. This diagnoses/addresses a lingering first-instance lock without weakening production sandbox or changing app startup semantics. The Linux result must be rerun and verified; no M05 restart completion is claimed yet.

### Linux window-selection root cause (2026-11-14)

The Linux restart fixture's first process printed PASS, and the second Electron process started, but the test waited for `BrowserWindow.getTitle() === "Cubics"`. The restart HTML explicitly includes a different `<title>`; Linux uses the page title for the native window, so this assertion could time out despite a healthy window. The fixture now looks up the real `BrowserWindow` by its **trusted local test origin**, then waits for its main-frame load, rather than a cosmetic title. Earlier SingletonLock/Xvfb explanations were diagnostic hypotheses, not verified product defects. This correction is test-only; final acceptance still requires a new successful three-platform CI run.

## M05 media signaling hardening (2026-11-14)

Legacy socket handlers now call the server-to-server PostgreSQL permission endpoint for every tab watcher, Live/Shared host registration and remote input event. Server confirms widget exists in that room and is actually Live or Shared. Only a Live widget's verified creator may host it; Shared hosting requires explicit consent from a room member. Remote input is limited to current watchers of a Shared session, with bounded allowed mouse/keyboard event fields. Host Stop or disconnect discards watcher state so a later host session needs fresh watching subscriptions.

Negative integration cases cover forged Live creators and widget modes, Live-only viewing without input, rejected unwatched Shared input, stripped arbitrary fields, invalid controller coordinates, and denial after Stop. **M05.05 is not yet complete:** LiveKit's room-scoped access tokens and active media connections require separate publisher-permission and removal/revocation hardening, plus production Clerk acceptance.

## M05 viewer-only LiveKit grants and widget publisher identity (2026-11-14)

The hosted LiveKit token API now issues **subscribe-only** room grants to ordinary viewers (`canPublish:false`), and grants publishing only on a separate short-lived session after authoritative DB lookup of an existing Live or Shared widget: Live only for its creator; Shared for an authorized room member. The publisher's signed identity is `host:<widget-id>:<nonce>` (no Clerk user ID in LiveKit identity/logs); the viewing client accepts a screen-share track only from that widget-specific publisher identity. On explicit host Stop/unmount, the publisher's track is unpublished and its dedicated LiveKit connection disconnected. Grants use a 5-minute join TTL and no-store token responses.

**Important remaining security limit:** LiveKit room-level tracks and already-connected participants are not forcibly evicted by this API alone. Server-side `RemoveParticipant` / revocation on membership changes, production two-account tests, and media race/abuse tests are still required before M05.05 or the milestone can be signed off. More publisher connections may affect LiveKit free-tier concurrency; test resource budget before scale.

## Obsolete media signaling attack-surface removal (2026-11-14)

GitHub repository-wide code search confirmed the current client uses `tab:*`/LiveKit and does not consume the old Socket.IO `sb:*` WebRTC offer/ICE/host events, `token:*` browser-controller queue, or `widget:input` relay. These old handlers could sidestep current widget-specific authorization and forward unaudited input. They were deleted, the exact security event inventory updated, and the alternate wildcard-CORS `src/socket-server.ts` entrypoint converted to an inert module. New same-room negative integration tests verify old peer/control packets are not forwarded, even between otherwise authorized members. This removes deprecated transport capability; future clients must use authenticated LiveKit and sanctioned `tab:*` events. M05.05 still requires active SFU revocation for removed room members.

## M05 member-list PII redaction (2026-11-14)

The legacy room member GET handler previously returned email addresses and loaded entire User records to all current room members. It now selects only the public room participant name and avatar from PostgreSQL and returns role/status metadata without email addresses; the list is explicitly private/no-store. The versioned member API already followed this policy. A negative regression test protects the legacy route. **M05.04 remains open** because historical Personal widget URLs may still be stored in PostgreSQL even though non-owners receive redacted HTTP metadata.

## Revoking active LiveKit participants on membership change (2026-11-14)

A server-only `RoomServiceClient` path now identifies media participants by an opaque room-scoped HMAC subject tag rather than public raw Clerk IDs. Membership removal calls LiveKit's `listParticipants` / `removeParticipant` before and after deleting the user's room membership; a legacy untagged LiveKit participant triggers a safe full-room reset because its owner cannot be determined. Deleting a whole Cubics room also invokes LiveKit `deleteRoom` before removing PostgreSQL data. If the provider is down at the initial eviction, removal is blocked with 503 and membership unchanged; after-DB failures return a 503 with `mediaRevocationPending`, not false success. No new token is granted to a removed user by the authenticated endpoint.

The second-pass provider error currently requires operator retry; there is not yet a durable revocation queue. LiveKit self-hosted servers can still accept an unexpired old token for up to the configured TTL even after removal. Therefore **M05.05 is not completed** until retry durability and self-hosted rejoin tests are implemented. Neither running tests against a fake provider nor static source inspection proves a production SFU was evicted.

### Provider compatibility and retry fix (2026-11-14)

The administrative LiveKit URL is normalized from browser `wss://`/`ws://` to `https://`/`http://` for `RoomServiceClient`. `listRooms([name])` treats a room with no active participants as an already completed eviction rather than a false provider outage. Room owners/admins can reissue the authenticated membership DELETE after an earlier partial failure to retry media cleanup even though the member record was already removed. There is still **no durable automatic retry queue** if the app or provider goes down at the second eviction attempt. M05.05 cannot be signed off until that is addressed and tested against a real SFU.

## LiveKit signed participant-joined authorization webhook (2026-11-14)

The Node `POST /api/livekit/webhook` endpoint verifies LiveKit's signature/JWT against the **raw** POST body before doing any authorization work. On a `participant_joined` event for a `cubics:<room-id>` media room, it compares the identity's room-scoped HMAC tag with the **current** PostgreSQL owner/member roster. A publisher is additionally validated against the current widget type and owner. Former members, deleted widgets and unrecognized/legacy identities are removed via the admin RoomServiceClient. Missing database/provider connectivity returns HTTP 503 for webhook retries, not implicit authorization. GET is not supported.

**Deployment action required:** Register this public HTTPS path in LiveKit Cloud's webhook settings or self-hosted `webhook.urls` using the same signing API key. The code itself does not create external webhook configuration. LiveKit webhooks occur **after** participant media establishment and delivery is best-effort; this guard cannot eliminate the interval before the webhook arrives or compensate for a permanently lost notification. M05.05 stays open until provider integration, cleanup retry durability and two-real-account acceptance tests are complete.

## Read-only cloud metadata exposure census (2026-11-14)

Run `npm run security:browser-metadata-audit` from a backend environment with `DATABASE_URL` to obtain only **aggregate counts** of cloud records containing Personal URLs/titles, Live URLs/titles, Shared full paths/query/fragment/custom titles and accidentally synced opaque BrowserProfile IDs. The scanner pages through Prisma in bounded batches and never prints any URL, title, account ID, widget ID or database error text. No mutation option exists, and it performs **zero UPDATE/DELETE operations**. This is a deployment-preflight instrument, not evidence that the legacy database has already been cleaned.

**Migration order (no data loss):** (1) Implement an Electron device-local OS-protected navigation vault, including strict Linux `basic_text` rejection; (2) load and verify the owner's existing URL from the legacy cloud record into the vault; (3) only after durable local confirmation, replace the cloud URL/title with a generic placeholder; (4) audit and scrub archived/backed-up records according to retention policies and explicit owner consent; (5) run a two-real-account privacy review. Until then, M05.04 and M05.07 remain unchecked.
