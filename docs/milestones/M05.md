## M05 profile lifecycle implementation — 2026-11-14

[Commit d8a9f378](https://github.com/ybcole/cubics/commit/d8a9f37827b660322956e84572c204d484367385) introduces a **separate non-persistent Shared profile** per verified Clerk account/widget on the current Electron device: `cubics-shared-<account>-<widget>` (no `persist:` prefix). It cannot silently inherit credentials from either the existing account-scoped persistent Personal profile (`persist:cubics-personal-...`) or a widget-scoped persistent Live profile (`persist:cubics-tab-...`). Only the main process creates and authorizes these partitions. User starts Shared hosting explicitly; the mode remains visible. Existing Personal and Live partitions are left unchanged to avoid unexpectedly losing saved sessions.

The Personal tab UI now offers **Clear local Personal browsing data**; Shared tabs provide a scoped clear control while not hosting. A native confirmation is required. Electron re-checks the authenticated identity after the dialog, derives its own partition name, requires a previously issued local session capability, destroys its active guests, and uses Electron 45 `Session.clearData()` for the selected partition. It notifies attached UI tabs to remount; it does **not** erase Clerk's default-session cookies, the database, another user's partitions, OS credential stores, saved downloads on disk, or historical cloud widget URLs. A cancelled dialog changes nothing.

[Cross-platform fixture commit 13f5042](https://github.com/ybcole/cubics/commit/13f50421095a454c5a1408362d62214e3f7228a6) additionally tests actual Chromium cookie jars across modes and account switches and verifies that clearing the Shared jar leaves Personal and Live cookies untouched. The fixture is simulated login, not real Clerk. **M05.01/M05.02/M05.03/M05.06 remain open for full milestone certification** (formal local BrowserProfile IDs/controls, actual Clerk two-account integration, OS-restart persistence, data export/deletion policy, and shared controller/consent E2E are not complete). Native matrix for the cookie assertion commit must finish successfully before it is called passing.

Security controls: [Electron main](../../electron/main.js), [profile policy](../../electron/security-policy.cjs), [native tests](../../scripts/security/electron-native-e2e.cjs), and [IPC inventory](../security/runtime-inventory.json). No provider or database migration was performed.

## Non-owner Live/Shared metadata hardening (2026-11-14)

In addition to Personal redaction, the legacy and versioned workspace widget reads now share the same `redactWidgetForViewer` function. Non-owner Live titles become `Live tab` and their URL is suppressed; non-owner Shared tabs show `Shared tab` and at most the origin (protocol/host/port) of the chosen site. Full paths, query strings, fragments and user-supplied titles remain visible to their owning account only. The v1 `safeUrl` summary never includes paths, even to the owner. Owner-controlled interactive Shared tab navigation still uses the full authenticated record in the host's view; a new host may need to navigate to the specific page after taking over. Per-mode safe site disclosure policy and negative tests are implemented, but existing cloud records still persist original URLs and actual two-account acceptance remains pending.

**Snapshot consistency:** The legacy v1 snapshot now uses the same server-side viewer redaction as both widget-list endpoints, preventing an unowned or non-owner Live/Shared title from bypassing the generic title policy. Read compatibility remains unversioned; this does not prove real multiaccount deployment or eliminate historical private URL records.

## M05 device-local BrowserProfile identity and metadata export (2026-11-14)

A new [Electron profile helper](../../electron/browser-profile.cjs) atomically persists one random non-secret device marker per Electron `userData` directory and deterministically derives opaque `bp1_...` BrowserProfile IDs from the device marker, **verified** Clerk account ID, mode and (for Live/Shared) widget ID. Room membership is not part of the identity. The profile ID is not a login token, not a security grant and never replaces the main-process authenticated partition check. Personal and Live cookie partition names are preserved; Shared remains temporary. Device markers/IDs stay on the device; no Prisma schema or cloud/sync records were changed.

Native `getBrowserProfileInfo` and `exportBrowserProfileInfo` IPC demand the current authenticated user and a previously issued partition. The Personal tab offers a **metadata-only** export through an OS save dialog; Electron verifies the account again before writing to a new local file. The JSON describes the opaque profile ID, mode and persistence but contains **no cookies, browsing history, site URLs, credentials, or raw account ID**. This is **not** a full browser-data export. Complete migration, account sign-out, profile inventory/retention and full export/delete remain M05.06 dependencies. Tests assert stable per-device/profile derivation and deny malformed identities.
