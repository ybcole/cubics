# M05 — Browser profiles, privacy isolation, and ownership

**Status:** IN PROGRESS · **Started:** 2026-11-14 · **Sign-off:** not granted.

## Implementation and evidence

- **M05.01/M05.02:** The existing Electron account-derived persistent partitions and local `userData` directory isolate browser storage; a formal durable BrowserProfile record/OS-level 2-user verification is not yet complete.
- **M05.03:** Live/Shared already use per-widget `persist:cubics-tab-<account>-<widget>` partitions, separate from Personal `persist:cubics-personal-<account>`. A native end-to-end profile/opt-in verification remains open.
- **M05.04 (partial):** Legacy widget GET now calls `redactWidgetForViewer` so non-owners and legacy ownerless rows get `Private tab` + `about:blank`. Socket.IO widget announcements transmit IDs only; geometry updates are bounded and metadata updates are opaque hints. Client re-fetches authorized data. See [privacy helper](../../src/lib/security/widget-privacy.cjs), [API](../../src/app/api/spaces/%5Bid%5D/widgets/route.ts), [socket](../../socket-server.cjs) and [negative tests](../../scripts/security/widget-privacy.test.cjs). Full sensitive URL removal from legacy PostgreSQL and per-mode policies remain incomplete.
- **M05.05–M05.08:** Not complete. Signed OS permissions, consent/revocation, local profile data lifecycle/export, secure secret storage and native two-account restart tests remain required.

## M05 profile lifecycle implementation — 2026-11-14

[Commit d8a9f378](https://github.com/ybcole/cubics/commit/d8a9f37827b660322956e84572c204d484367385) introduces a **separate non-persistent Shared profile** per verified Clerk account/widget on the current Electron device: `cubics-shared-<account>-<widget>` (no `persist:` prefix). It cannot silently inherit credentials from either the existing account-scoped persistent Personal profile (`persist:cubics-personal-...`) or a widget-scoped persistent Live profile (`persist:cubics-tab-...`). Only the main process creates and authorizes these partitions. User starts Shared hosting explicitly; the mode remains visible. Existing Personal and Live partitions are left unchanged to avoid unexpectedly losing saved sessions.

The Personal tab UI now offers **Clear local Personal browsing data**; Shared tabs provide a scoped clear control while not hosting. A native confirmation is required. Electron re-checks the authenticated identity after the dialog, derives its own partition name, requires a previously issued local session capability, destroys its active guests, and uses Electron 45 `Session.clearData()` for the selected partition. It notifies attached UI tabs to remount; it does **not** erase Clerk's default-session cookies, the database, another user's partitions, OS credential stores, saved downloads on disk, or historical cloud widget URLs. A cancelled dialog changes nothing.

[Cross-platform fixture commit 13f5042](https://github.com/ybcole/cubics/commit/13f50421095a454c5a1408362d62214e3f7228a6) additionally tests actual Chromium cookie jars across modes and account switches and verifies that clearing the Shared jar leaves Personal and Live cookies untouched. The fixture is simulated login, not real Clerk. **M05.01/M05.02/M05.03/M05.06 remain open for full milestone certification** (formal local BrowserProfile IDs/controls, actual Clerk two-account integration, OS-restart persistence, data export/deletion policy, and shared controller/consent E2E are not complete). Native matrix for the cookie assertion commit must finish successfully before it is called passing.
